## 引言

走进任何一个工业装备展会，或者站在任何一台国产或进口设备前面，你大概率会看到这样的触摸屏：五颜六色的按钮挤满整个屏幕，到处是方框，参数密密麻麻地排列，屏幕底部滚动着一行报警文字。

我所在的公司是一家专门为 OEM（设备制造商）提供 HMI 设计与开发服务的乙方公司，接触过 300 多家公司的项目，其中包括施耐德这样的行业头部企业。坦白说，我们几乎没有见过真正好的 HMI。展会上的情况也一样。

过去我们把这些问题简单概括为“界面丑、没交互、业务逻辑不清晰”，并且一直在一个个项目中尝试改善它们。但时间越长，我们越清楚地意识到：单靠设计一个好的界面，甚至做一套设计系统，都解决不了根本问题。

这篇文章记录了我们的一次系统梳理：从具体现象出发，逐层追问原因，最终把这些现象和产业结构联系起来。我们的目的不是给出解决方案，而是先把问题描述清楚。

## 一、我们的观察位置

讨论问题之前，先说明这些观察从哪里来，以及它们的局限。

**观察来源**

- 项目：300 多家 OEM 客户的 HMI 项目，覆盖多个装备行业，包括行业头部企业
- 展会：国内外工业装备展会上的现场观察
- 过程：作为乙方，我们不只看到最终界面，也看到了界面从需求、设计、实现到交付的整个过程

**需要承认的局限**

- 样本偏差：会来找设计方的客户，通常是对现状不满意的客户。做得好的公司不会来找我们，所以我们的项目样本天然排除了“好的例子”。展会观察可以部分弥补这个偏差，但不能完全消除。
- 以中国市场为主：我们的项目主要来自国内 OEM。认为“全球普遍存在”，依据的是展会观察和国际客户项目，还需要更系统的跨地区证据。

## 二、现象：我们看到了什么

我们把判断（“丑”“难用”）和解释（“工程师不懂设计”）先放在一边，只描述可以观察到的事实。

### 现象 1：报警只有“跑马灯加列表”

大多数设备的报警功能由两部分组成：屏幕顶部或底部的滚动跑马灯，以及一个独立的报警列表页。列表通常只有时间、报警文本和状态等字段。

在一次完整的异常处置中，操作员需要的其他环节基本都缺失：

- 无法从报警直接跳转到对应的设备或页面
- 没有原因说明和处理建议
- 没有恢复确认的过程
- 没有对历史报警的统计和分析

### 现象 2：首页没有明确定位

首页通常平铺着大量按钮和参数，占满整个屏幕，所有元素的视觉权重基本相同。区域划分几乎完全依靠边框和分组框，到处都是“框框”。

操作员看完首页，无法很快回答三个最基本的问题：设备现在是否正常？正在做什么？我下一步该做什么？

### 现象 3：没有导航层级

很多界面没有始终可见的全局导航，而是单独做一个导航页面，放几个色块按钮。页面之间是平铺关系，没有“总览 → 单元 → 详情”这样的层级结构。

### 现象 4：视觉没有规范

同一个界面里同时使用多种高饱和度的颜色，颜色不表达任何含义，同一种颜色在不同地方代表不同意思。图表、间距、字体和图标在不同页面之间各不相同，甚至同一个页面里也不统一。不同型号设备之间更是如此。

### 现象 5：好的设计在工具里实现不了

设计交付后，客户会在自己采用的触摸屏品牌配套的组态软件里还原设计。很多组态软件功能有限，比如报警通常只有一个组件，也就是一个列表。所以，即使我们设计出了更好的报警方案，在组态软件里也常常无法实现。

### 现象 6：客户的需求来自“竞争力”

OEM 来找我们，主要是为了提升设备竞争力，常见的触发点是参加展会、出口海外。

### 现象 7：预算普遍很低

预算低是普遍现象。我们接到过的最大项目约为 10 万元，内容包括设计和程序开发，客户是一家制药企业。在预算充足的项目里，组态软件的限制基本都能绕过，甚至可以换一条技术路线。

### 现象 8：OEM 内部没有 HMI 设计团队

在我们接触过的 OEM 中，HMI 一般由自动化工程师或电气工程师绘制，或者外包给第三方。我们没有见过哪家 OEM 有专门的 HMI 设计团队。

## 三、第一层抽象：有元素，没有结构

把现象 1 到 4 放在一起，可以看到它们分别落在三个层面，而且每个层面的问题是同一种：

| 层面   | 有什么           | 缺什么                                     | 对应现象  |
| ------ | ---------------- | ------------------------------------------ | --------- |
| 视觉层 | 颜色、字体、图表 | 视觉系统：颜色没有语义，样式没有规则       | 现象 4    |
| 信息层 | 页面、按钮、参数 | 信息架构：首页没有定位，页面之间没有层级   | 现象 2、3 |
| 任务层 | 报警数据         | 处置流程：从发现异常到恢复正常的路径不存在 | 现象 1    |

可以概括为一句话：

> 界面里有元素，但没有结构。

再往下看一层，这三类缺失有一个共同特征：界面是按“系统里有什么”来组织的，而不是按“人需要什么”来组织的。

- 首页等于参数列表：PLC 里有哪些参数，就摆出哪些
- 导航页等于页面清单：程序分了几个模块，就放几个按钮
- 报警页等于报警表：系统里有一张报警表，就原样显示出来

由此得出第一个核心判断：

> 今天的 HMI 是控制程序在屏幕上的投影，而不是为操作员设计的工作工具。

以报警为例。从操作员的角度看，一次异常处置应该是一条完整的路径：

**感知 → 理解 → 定位 → 诊断 → 处置 → 确认恢复 → 记录**

而从更长的时间尺度看，报警数据还应该进入另一个循环：统计哪些报警最频繁、哪些报警长期存在、哪些报警毫无意义，进而优化报警设置，甚至改进设备本身。

现实中的“跑马灯加列表”，只覆盖了这条路径的第一步。

## 四、直接成因：界面是怎样被生产出来的

为什么界面会成为控制程序的投影？只要看看一块 HMI 是怎样产生的，答案就比较清楚了。

| 追问         | 现状                                                               |
| ------------ | ------------------------------------------------------------------ |
| 谁在做？     | 自动化或电气工程师。他们的专业是控制逻辑，而不是人因工程和交互设计 |
| 用什么做？   | 触摸屏厂商配套的组态软件，基本模式是“画图形 + 绑定变量”            |
| 依据什么做？ | I/O 表、控制程序和功能说明，里面没有操作员的任务和使用场景         |
| 什么时候做？ | 往往在项目后期，甚至在现场调试时边调边改                           |
| 怎么验收？   | 功能正常、点位都通                                                 |
| 交付以后？   | 基本不再迭代，设备一用就是十几二十年                               |

这里特别要说的是工具。

现象 5 告诉我们，报警只有“跑马灯加列表”，并不仅仅是因为工程师没想到，更是因为组态软件里只有这一个报警组件。工具厂商对“报警”的理解就是一张列表，这种理解通过工具被复制到了成千上万台设备上。

> 工具决定了界面的上限。

组态软件提供的是绘图层面的底层图元，比如矩形、文本、变量绑定，而不是业务层面的结构，比如报警处置流程、设备状态、操作模式。工程师在这样的工具里，自然只能画出“有元素、没有结构”的界面。

## 五、经济约束：好的 HMI，感知价值低于实现成本

我们最初认为，预算低是核心问题。确实，预算是最直接的约束：现象 7 显示，只要预算充足，连工具的限制都能绕过去。

但继续追问“为什么预算普遍这么低”，会发现预算低本身是一个结果。它来自两边的落差：

> 感知价值 < 实现成本
>
> 客户认为 HMI 值多少钱 < 做好一套 HMI 实际要花多少钱

### 价值侧：为什么感知价值低？

- 需求停留在外观层。 现象 6 显示，OEM 找设计方是为了展会和出口，也就是为了让设备“看起来有竞争力”。这个市场中已经存在的需求，是面向买家的外观需求，而不是面向操作员的使用需求。
- 使用者的痛苦传不回付费方。 付钱的是 OEM，每天使用设备的是终端工厂的操作员。界面导致的低效、误操作和培训成本，发生在终端工厂；而且这些代价往往被归结为“操作员失误”或“培训不到位”，很少被追溯到界面设计。
- 我们推测，客户可能会拿屏幕硬件的价格作为参照，来衡量 HMI 应该值多少钱，这一点还需要验证。

### 成本侧：为什么实现成本高？

- 工具受限：要做好，就得定制开发，甚至换技术路线
- 没有内部能力：OEM 没有设计团队，只能外包
- 没有可复用的资产：没有行业通用的规范、组件和方法论，每个项目都从零开始

所以，“预算低”和“工具受限”不是两个独立的问题，而是同一个问题的两面。需求停留在外观层，预算就只够做外观；业务逻辑、交互和报警流程这些更深层的部分，自然没有空间去做。这也解释了为什么即使请了设计方，问题也只能被部分解决。

## 六、产业结构：为什么全行业长期如此

经济约束解释了单个项目为什么做不好。但为什么整个行业长期如此？我们认为有四个结构性原因。

### 1. HMI 没有“主人”

产业链上有设备制造商、触摸屏和组态软件厂商、系统集成商、终端工厂。每一方都只负责自己那一段，“操作员用起来好不好”不在任何一方的职责里。

现象 8 从组织层面印证了这一点：OEM 内部没有 HMI 设计岗位，说明 HMI 不被视为一项需要专门能力的产品职能，而是电气工程的一个附属环节。没有岗位，就没有人负责积累，也没有人推动改进。

### 2. 付费者与使用者分离

做决策和验收的是 OEM 与终端工厂的采购、工程部门，承受后果的是操作员。前者感受不到痛苦，后者没有话语权。

### 3. 规模不经济

我们认为这是最核心的结构原因之一。

做好 HMI 需要一笔固定投入：设计规范、组件库、方法论和开发能力。但装备行业由成千上万家 OEM 组成，型号多、批量小，每家各做各的。这笔固定投入被拆成了无数份，每一份都小到不值得投入，也无法在彼此之间分摊。

对比一下：消费级软件可以把设计成本分摊到几百万用户身上。而海事领域的开源设计系统 OpenBridge，则是通过研究机构牵头、多家厂商共同参与，把单个厂商承担不起的设计投入，变成了整个行业共享的资产。

这从另一个角度说明了为什么单个界面解决不了问题：单个项目的投入永远在门槛以下。

### 4. 工具生态碎片化且封闭

触摸屏厂商众多，各有私有的组态软件，彼此不兼容。即使有人做出了好的规范，也没有一个通用载体把它带到所有项目中。同时，工具本身的抽象层级很低，进一步限制了界面质量的上限。

**这四个原因相互强化**

- 职责缺位和利益错位，让这件事没有动力
- 规模不经济和工具碎片化，让这件事没有能力

没有动力，也没有能力，问题就会稳定地长期存在。

## 七、完整的问题结构

把所有现象和推断串联起来：

```text
【界面现象】
  有元素，没有结构
  视觉无系统 / 信息无架构 / 报警无流程
              ↑
【直接成因】
  由工程师绘制（缺乏设计能力）
  在受限的组态软件中实现（工具决定上限）
  依据控制程序组织（按系统有什么，而不是人需要什么）
              ↑
【经济约束】
  好的 HMI：感知价值 < 实现成本
  价值侧：需求停留在外观层，操作员的价值传不回付费方
  成本侧：工具受限、无可复用资产、无内部能力
              ↑
【产业结构】
  HMI 没有主人（组织中无岗位）
  付费者与使用者分离
  OEM 高度分散，固定投入无法分摊（规模不经济）
  工具生态碎片化且封闭
```

**问题陈述**

> 在装备制造业，人机界面普遍呈现出“有元素、没有结构”的状态：视觉缺乏系统，信息缺乏架构，异常处置缺乏流程。
> 直接原因是，HMI 由缺乏设计能力的工程师，在功能受限的组态软件中，依据控制程序而不是操作任务来实现。
> 更深层的原因是，好的 HMI 的感知价值长期低于实现成本：一方面，市场对 HMI 的需求停留在外观层面，操作员层面的价值无法传递给付费方；另一方面，行业由大量分散的 OEM 组成，做好 HMI 所需的固定投入无法分摊，每个项目的预算都低于门槛，再加上工具生态的碎片化，进一步推高了实现成本。
> 因此，在单个项目或单个界面层面的改进，无法改变这种状况。

## 八、为什么单点改进无效

有了这个结构，就可以理解为什么常见的改进方式都只能部分起作用：每一种都只作用于链条上的某一个环节。

| 改进方式                        | 作用的环节     | 没有触及的环节                                                           |
| ------------------------------- | -------------- | ------------------------------------------------------------------------ |
| 为单个项目设计好的界面          | 界面现象       | 工具限制、预算门槛、无法复用，下一个项目又回到原点                       |
| 制定一套设计系统                | 设计知识的缺失 | 工具实现不了，没有人负责执行，没有载体传播                               |
| Web 化、去组态化的新型 HMI 工具 | 工具的表达上限 | 谁来设计、依据什么设计、怎么验收；自由度更高但缺乏约束，结果可能更加混乱 |
| 加强工程师培训                  | 个人能力       | 预算、工具和组织岗位的缺失                                               |

这也是我们在实践中反复碰壁的原因。

### 其他领域的参照

值得注意的是，相关知识其实早就存在：

- 流程工业有 ISA-101（过程自动化 HMI 标准），定义了 HMI 的生命周期和显示层级
- 报警管理有 ISA-18.2 / IEC 62682 和 EEMUA 191，定义了报警的完整生命周期、状态模型和评估指标
- 离散制造有 PackML（ISA-TR88），定义了标准化的设备状态模型
- 海事领域有 OpenBridge，在研究、行业联盟和法规的共同推动下，建立了跨厂商的设计系统

但这些知识很少进入装备制造业的日常实践。缺的不是知识本身，而是让知识落地的结构：抽象的标准和具体的组态操作之间，缺少一个翻译层；单家企业的投入，又不足以支撑这个翻译层。

---

## 九、尚待验证的问题

这次梳理基于我们自己的项目经验和展会观察，有些环节目前还只是推断，需要进一步验证：

1. 价值侧的证据：终端工厂在采购设备时，是否评估过 HMI？是否向 OEM 投诉过界面问题？因界面导致的误操作和停机，最后被归因到了哪里？
2. 价格参照：客户是否会以屏幕硬件的价格作为心理参照，来衡量 HMI 的价值？
3. 例外的研究：流程工业、高端机床、医疗设备、海事等领域里做得相对好的案例，它们消除了上述哪些结构原因？例外能反过来检验我们的分析是否成立。
4. 地区差异：欧洲、日本、北美的装备企业是否存在同样的问题？如果程度不同，差异来自哪里？
5. 量化：HMI 投入占设备总价的比例是多少？一家 OEM 每年在 HMI 上花费多少工程师工时？

---

## 结语

过去我们一直在问：“怎样把这个界面做好？”

这次梳理让我们意识到，更准确的问题是：为什么整个行业做不好界面，并且一直做不好？

答案不在界面本身，而在界面背后的生产方式、经济约束和产业结构。HMI 的困境，本质上是一个结构性问题：它没有主人，它的价值没有被看见，它所需的投入无法被分摊，它的载体是碎片化的。

把问题描述清楚，是解决问题的第一步。我们希望这篇文章能让更多同行，包括 OEM、触摸屏和组态软件厂商、系统集成商、终端工厂，以及设计和研究人员，看到这个问题的全貌，而不只是看到屏幕上的那些框框。
